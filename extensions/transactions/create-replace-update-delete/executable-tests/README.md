# Executable tests

Executable tests for the Abstract Test Suite (Annex A) of *OGC API - Features -
Part 4 / OGC API - Common - Part 5: Create, Replace, Update and Delete*, together
with a test deployment that publishes the [test dataset](../standard/data) of the
Standard.

The tests were used while drafting the Abstract Test Suite, to verify that the
tests are executable and that the requirements are testable. They are not an
official Executable Test Suite of the OGC.

## Prerequisites

* Docker with Docker Compose
* Python 3 (the test runner only uses the standard library)
* `curl`

## Running the tests

```sh
./run-tests.sh                                   # all applicable tests
./run-tests.sh --only /conf/features             # one conformance class
./run-tests.sh --only /conf/features/geojson     # one test
./run-tests.sh --verbose                         # log every request
docker compose down                              # stop the deployment
```

`run-tests.sh` starts the deployment, waits until the API is available and
executes the tests. With `--verbose`, every test is announced with its purpose
from the Abstract Test Suite and every request is preceded by a line stating what
that request tests:

```
  ---- /conf/optimistic-locking-timestamps/replace: Conditional REPLACE operations using If-Unmodified-Since
      · GET the feature to obtain its Last-Modified value for the preconditions
      > GET http://localhost:7080/buildings/collections/buildings/items/B.2 -> 200
      · PUT with an If-Unmodified-Since value BEFORE the last change: the precondition fails (412) and the feature is unchanged
      > PUT http://localhost:7080/buildings/collections/buildings/items/B.2 -> 412
``` Since the tests change the resources of the API, the test
dataset is reloaded before each conformance class.

Each test evaluates the conditions in its "Condition" row against the
conformance declaration of the API under test and the test parameters; a test
whose conditions are not met is reported as `SKIP`, with the reason. Only the
conformance class URIs of this Standard are recognised, that is
`http://www.opengis.net/spec/ogcapi-common-5/1.0/conf/…` for the five
conformance classes that are shared with OGC API - Common - Part 5 and
`http://www.opengis.net/spec/ogcapi-features-4/1.0/conf/features` for the
Features conformance class. An implementation that declares the URIs of an
earlier draft therefore reports all classes as not declared and all tests are
skipped; `--assume <conformance class>` runs them anyway.

To run the tests against another Web API, call the test runner directly:

```sh
python3 ats/run_ats.py --landing-page https://example.com/api --collection buildings
```

Options: `--put-create-collection` names a collection that supports creating
resources with PUT, `--reset-cmd` a command that restores the test dataset,
`--data-dir` the directory with the test dataset (default: `../standard/data`),
`--assume` treats a conformance class as declared, `--only` filters tests.

## The test deployment

The deployment uses [ldproxy](https://github.com/ldproxy/ldproxy) on a PostGIS
database. The database is a throw-away instance (`tmpfs`) that creates the tables
and loads the test dataset on startup, see [sql](sql).

The deployment publishes two APIs and three collections, so that the conditions
of all tests are met by at least one of them:

| API | Collection | Purpose |
| --- | --- | --- |
| `buildings` | `buildings` | the resource under test for most tests: the server assigns feature identifiers, optimistic locking using timestamps is supported |
| `buildings` | `buildings_upsert` | the same buildings with client-assigned identifiers, so that new features are created with PUT — the collection declares `supportsNonAutogeneratedResourceIds: true`. Optimistic locking is not supported for this collection: a PUT that creates a feature has no previous state, so requiring a precondition would make that case untestable. |
| `buildings-nocrs` | `buildings` | the same features without support for coordinate reference systems other than WGS 84 longitude/latitude. This is the deployment required by the condition of `/conf/features/crs84`; since a conformance declaration is per API, this cannot be a second collection. |

The APIs support GeoJSON, JSON-FG and GML in mutation requests, JSON Merge Patch
for UPDATE operations, the `Prefer` header with the handling preference, and they
publish the schema of the collections. The API also publishes the GML application
schema of the test dataset, so that `xsi:schemaLocation` in GML responses can be
resolved; `ldproxy/resources/api-resources/buildings/buildings.xsd` is a copy of
[buildings.xsd](../standard/data/buildings.xsd) from the test dataset.

## Result

Executed on 2026-08-21 with the test dataset of this Standard. The result: 
**30 of 34 tests pass**, 4 skipped, none failed.

The four skipped tests are the tests of the conformance class "Optimistic Locking 
using ETags", which the implementation does not support. All other tests are 
applicable and pass; that is, every requirement of this Standard was verified 
against an implementation.

The run predates the conformance class "Return Resource Representation in 
Response". Its five tests have not been executed yet; the implementation does not 
declare the conformance class, so they are reported as skipped until the test 
deployment supports the `return` preference.
